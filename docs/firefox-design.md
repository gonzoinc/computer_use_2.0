# Firefox direct debugging design and evidence

Current decision: **extension-free direct Firefox RDP**. The user rejected the temporary-add-on deployment route. The final Firefox component has no extension, signing step, native-messaging registry key, or original OpenAI dependency. Earlier extension/native-pipe prototype source was removed only after its direct replacement passed actual Firefox acceptance.

## Launch, local binding and existing sessions

The main `C:/Program Files/Mozilla Firefox/omni.ja` entry `moz-src/devtools/startup/DevToolsStartup.sys.mjs` has SHA-256 `bec6232a2fbad4882ae8449a43d479cbd06b7aebd4e52276449c96590f87de1a`.

Its `handle` method at375-380 explicitly handles calls after browser startup. Lines436-437 invoke the debugger-server handler outside the initial-launch branch; lines1340-1341 handle `STATE_REMOTE_AUTO` without opening a surplus window. Thus command forwarding to an existing running browser is a source-backed possibility, not an inherently restart-only architecture. Windows forwarding to the user's current live profile has not been executed or verified.

The startup gate at23-25 and1168-1188 requires `devtools.debugger.remote-enabled=true` and `devtools.chrome.enabled=true`. The server starts with `--start-debugger-server PORT`; lines1311-1316 keep it alive for the process lifetime and register actors. Future browser processes need the startup flag again. Preferences alone do not launch a listener. A coordinated normal relaunch may be needed if forwarding fails; the adapter never force-kills/restarts an existing user browser.

`shared/security/socket.js:392-413,496-499` refuses opening a listener without remote-enabled and binds only loopback when force-local is true. `shared/security/auth.js:168-175` preserves its normal approval prompt unless prompt-connection is false. The final launcher requires an explicit profile and explicit local port, checks that the port is free before launch, and explicitly requires force-local true. Its opt-in profile setup writes only a recognizable three-preference block while the profile is closed. It leaves connection approval unchanged. No custom recurring approval-token system exists.

The isolated acceptance fixture alone sets prompt-connection=false in its own disposable profile, as authorized for testing. No user profile, live tab, cookie, preference, registry key, or browser installation was changed. The real user-profile activation remains a separate step.

## Implementation contract and actual checks

`firefox/bridge.mjs` exports `FirefoxBridge` and `FirefoxTools`. Startup is idle; connection/launch/profile setup require explicit tools. `close()` disconnects RDP only. The runtime has no npm dependencies. RDP frames use UTF-8 byte lengths, not character lengths. Long-string retrieval enforces output byte bounds without corrupting Unicode; bulk transfers fail explicitly. Actor IDs are connection/document scoped. Reconnect discards sessions and never replays mutations.

Default `node --test firefox/*.test.mjs` does not launch Firefox. Latest author result after connection repair: **27 passed, 0 failed, 1 intentionally skipped live test**. Tests cover real socket framing, split/coalesced Unicode packets, unsolicited events, per-actor ordering, cross-actor concurrency, timeout/cancel without queued mutation replay, malformed/oversized/bulk packets, source-map mapping, opt-in profile setup/removal/idempotence, provenance restoration/conflict refusal, stalled TCP expiry, delayed approval, default pending/status/failure including launch preparation and disconnect/close cancellation, explicit normal-window destination validation and profile-name/path discovery using owned fixture files only.

Explicit live command (PowerShell): set `CU2_FIREFOX_LIVE=1`, run `node --test firefox/direct.test.mjs`, then remove that environment variable. Author result: **2 passed, 0 failed/skipped** against an actual isolated headless Firefox159 process automatically launched through the exported browser.launch tool. The test owns its local HTTP fixture and disposable profile, checks cleanup remains under primary project .codex, and stops only its exact spawned browser tree.

The real browser test verifies DOM and computed CSS, synthetic click/fill and temporary style edits; retained native console messages and native page exceptions; successful and404 request metadata/status plus response bodies; byte-bounded Unicode bodies; source actors/content and external source maps; a mapped breakpoint in an actual page timer/button callback; native pause reason, stack and lexical variables; frame-scoped evaluation; real step-over, resume and immediate interrupt; a PNG screenshot of the exact browsing context; new-tab creation; navigation/reload actor switching; cancellation and explicit reconnect with fresh sessions. The breakpoint resolves a mapped column0 to an actual breakable column17; blindly setting unbreakable column0 did not pause and was corrected.

## Repairs following independent review

`tabs.create` now requires an explicit normal windowId returned by `windows.list`; this is the chrome-window browsing-context ID, not an operating-system handle. The same synchronous chrome operation rechecks that the exact window is open/non-private before addTab. No most-recent-window fallback remains. Fake tests cover a private most-recent window, ambiguous normal windows, closed/missing IDs and privacy changes after discovery. The actual Firefox fixture verifies the returned ID and destination.

Profile setup now records original targeted boolean values before activation in the owned `computer-use-2-profile-setup.json` record. Closed-profile restoration removes the recognized user.js override and restores any materialized prefs.js values (including absence), preserving unrelated settings and comments. The record has a checksum for accidental edits, path/schema checks and recoverable prepared/active/removing phases. It is local recovery metadata, not a security boundary against a malicious same-user editor or a whole-profile backup. Changed targeted values, unsupported custom preference JavaScript, edited/missing provenance or a locked/live profile are refused instead of overwriting uncertain state. Tests include simulated Firefox persistence and actual isolated launch/setup/live-refusal/closed-restoration.

The original three-second repeated greeting attempts were removed. Browser launch/connect expose startupTimeoutMs (default30seconds,max120seconds) and approvalTimeoutMs (default15minutes,max1hour). The initial TCP socket now has its own remaining startup timer; a never-connected socket expires against that timer, not the approval budget. Only refused pre-TCP startup attempts retry; once TCP connects, a fresh single approval timer begins and its socket remains open for Firefox's native approval/greeting. The ordinary15-second actor timeout is separate. A stalled socket with25ms startup/1000ms approval expired in31ms; a fake server delaying greeting3.2seconds still uses one accepted connection even with100ms actor timeout.

The root runtime has no extra timeout, but Codex's [official MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) and [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) document a default60-second tool timeout for regular MCP servers. Plugin-scoped policy examples do not establish a supported timeout override. No client/global configuration is changed or undocumented plugin field invented.

Therefore default `browser.connect`/`browser.launch` return promptly with pending state while one background job owns the socket. `browser.status` reports connected/pending and connectionOperation state/error; `browser.disconnect` cancels startup/approval and clears actor state. `close()` also cancels. Neither closes Firefox nor restores an already-configured profile; completed setup remains explicitly restorable. A duplicate pending begin fails BUSY without a new socket; an active connection must be explicitly disconnected before replacement. Short-call completion/cancellation does not later tear down its approval socket. No mutation is replayed. `waitForConnection:true` is synchronous expert direct-API/testing only, not the agent default. Fake tests verify prompt return before delayed greeting, completed caller signal detachment, duplicate rejection, background errors and cancellation. The real isolated fixture uses default async launch followed by status readiness before all feature checks. Existing signed-in user-profile launch and native approval remain a coordinated readiness-gated activation step.

## Remaining practical limits

Full existing signed-in user-profile launch, Windows existing-process forwarding, multi-profile routing, private browsing and all browser-version combinations are not verified. Initial page-target scope is HTTP/HTTPS; private targets fail explicitly. Page DOM actions are synthetic and may not satisfy trusted user gestures. Page outputs are untrusted. Native console history and response bodies depend on Firefox's retained resources, not unlimited historical recovery. Source maps support flat version3 only. Native window/Firefox chrome manipulation remains the independent Windows driver's responsibility. No generic raw-packet command is presented as proof that unsupported features exist.
